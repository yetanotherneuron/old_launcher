# Developing Old Launcher

What the [README](README.md) leaves out: how the catalog and the list of
mods are built, what the app does to a client folder, how the code is laid
out, and how to test it.

## The catalog

`index/wotlk.json` is the launcher's own catalog, generated by the `indexer`
tool and committed here:

```sh
GITHUB_TOKEN=$(gh auth token) cargo run --release -p indexer   # writes index/wotlk.json and index/archives.json, then the mods (see below)
```

The token only raises GitHub's API limits: a run makes about a hundred
calls, more than GitHub allows anonymously.

The indexer lists every upstream source, downloads every archive except
the unchanging ones it inspected before (see below), and records the addon
folders each one installs (with their `.toc` title,
version and interface), when it was last updated, and the addon's own page
and history of changes at the source when it has them. Listings that install
the same folders are merged into one entry whose downloads are ordered
newest first (by version when the versions have the same shape, by date
otherwise), those made for 3.3.5a before the rest. An entry no source
describes takes the `## Notes` of its first folder that has some, as the
game's own addon list shows them. Entries whose download
is dead, holds no addon or declares a later expansion's interface are left
out and reported, and links to dead or hijacked sites are dropped.

The sources, in order of preference (the first one listing an addon
describes it):

- [NoM0Re/WoW-3.3.5a-Addons](https://github.com/NoM0Re/WoW-3.3.5a-Addons),
  a curated collection, together with NoM0Re's own addon repositories.
- [locus313/WoW-3.3.5a-Addons](https://github.com/locus313/WoW-3.3.5a-Addons),
  a curated collection of backports.
- Backport maintainers on GitHub (ElvUI-WotLK, bkader, Bunny67, Zidras,
  s0h2x, KhalGH, Sattva-108, Xurkon, Wrath-AddOns): their own repositories
  that declare the 3.3.5a interface, and the forks named in `github::FORKS`,
  which carry backports of their own.
- Addon authors on GitLab (juxuanu): only the projects named in
  `gitlab::AUTHORS`, since GitLab doesn't tell anonymous callers how big a
  project is, and listing every project of an author would download them
  all.
- [WoWInterface](https://www.wowinterface.com), through the public API addon
  managers use (`api.mmoui.com`). It tags files with game versions only from
  Wrath Classic (3.4) on, so the indexer takes the untagged addons whose
  latest file came out while 3.3 was the live patch (2009-12-08 to
  2010-10-12) and keeps those that declare the 3.3.5a interface, but for a
  few uploads left out by id (`wowinterface::EXCLUDED`), such as someone's
  whole AddOns folder uploaded as one addon. Addons
  still maintained today aren't there in their 3.3.5 version: the site keeps
  only recent old versions.
- [Rising Gods](https://addons.rising-gods.de/addons), a server's collection
  (descriptions in German).

An addon's update date is the newest file date inside its archive, which for
a repository snapshot is its last commit. locus313's zips are rebuilt daily,
so for those it is the last commit touching the addon's folder. WoWInterface
gives the upload date of the file.

Some archives never change: a new version gets a new URL, as WoWInterface's
links carry the upload time. What the indexer finds in those (folders,
`.toc` fields and date) goes to `index/archives.json`, by URL, whether the
listing made it into the catalog or not, and the next run reuses it instead
of downloading the archive again. A source says so per listing
(`Listing::immutable`). Branch snapshots and rebuilt zips change under the
same URL, so they are downloaded every run. Without the file, every archive
is downloaded again, so delete it after changing how archives are inspected
(`Contents::inspect`), or the old findings stay.

The app fetches the published catalog, `index/wotlk.json` as committed on
`main`, which a weekly CI schedule regenerates, and keeps the last copy
fetched in `~/.cache/old_launcher` (`%LOCALAPPDATA%\old_launcher` on
Windows), so the catalog shows instantly and offline from the second run
on. A refresh asks the repository whether the catalog changed before
downloading it.
`OLD_LAUNCHER_INDEX=<url or path>` at run time points the app at any other
catalog, such as a local `index/wotlk.json` while working on the indexer.

Sources live in `indexer/src/source/`, one module each, as types
implementing the `Source` trait (`info` describes it for the catalog, `list`
returns its listings). Adding one means writing that module and adding it to
the ordered list in `indexer/src/main.rs`; a GitHub maintainer is one more
name in `github::MAINTAINERS`, and a GitLab project one more path in
`gitlab::AUTHORS`.

The word "catalog" never appears in the app's own text: users see "the list
of addons", what is "available" and what is "up to date". It stays in the
code, the logs and here.

## The mods

`index/mods.json` lists the mods: changes to a client outside
`Interface/AddOns`, such as a DLL the game loads beside `Wow.exe` or a
patched archive in `Data`. The same indexer run writes it, and the same
schedule commits it (`--mods-only` builds it alone, leaving the catalog as
it is). A release the indexer doesn't understand (new setup scripts, a
file not where it was) is left out rather than guessed at, and the
launcher goes on offering the last one listed; when that leaves a mod's
newest release out, the indexer exits with code 3 after writing, and the
schedule commits what it wrote and then fails, so its owner is mailed the
reason, which says what to teach the indexer. Each mod says what it is
and where it comes from, and lists its
releases, the newest first: where to download each (an archive of its
files, or its one file itself) and every file it puts in the client folder,
by path, with its SHA-256. An archive holds them at the same paths, or in
the folder a release names as `inside` (the rest of the archive is left
out). Mods that need more say so: their `settings` (the player's files,
never checked and kept by a reinstall), what they write as they run
(`writes`), the
`setup` each release runs once its files are in place (the file each step
`creates` tells whether it ran), the `config` `WTF/Config.wtf` must set,
the `platforms` they are for (`windows`, `linux`, `macos`; all when
none), the launcher listing only those for its own, and `version_in`:
where their files say their version when not in their version resource
(DXVK's DLL says Windows' own there, to pass for it, and its own after
`DXVK: ` in the file), read of a copy installed by hand.

Each mod has a module in `indexer/src/mods/`, called from `mods::gather`,
which finds its releases and writes down what can't be read from them. The
indexer hashes every file of every release's download; what it found goes
to `index/mod-archives.json`, by URL, for the next run to reuse, since a
release's download never changes. Lumenveil's module reads its GitHub
releases, checks each zip against the release's `SHA256SUMS.txt`, and knows
its setup, what it writes and which files are the player's from its
`Lumenveil-Setup.cmd` and `Lumenveil-Uninstall.cmd`. A release whose scripts
it doesn't know, by checksum, is left out and reported, so the launcher
goes on offering the last one it understands until the module learns the
new scripts. DXVK's module lists the 32-bit `d3d9.dll` of every release from
1.5, the first with Direct3D 9, inside each release's tarball
(`dxvk-<version>/x32`), for Windows only: Proton, Lutris and the like bring
their own.

The app fetches, keeps and refreshes `index/mods.json` as it does the
catalog; `OLD_LAUNCHER_MODS=<url or path>` points it at another one.

## How it works

There is no database. Everything is read from the client folder itself:

- **Installed addons**: every folder in `Interface/AddOns` and its `.toc`.
- **Where an addon came from**: installing drops a small
  `.old_launcher.toml` marker (source, catalog entry, URL) into each folder
  it creates, with every file it put there (SHA-256, length and time). The
  client ignores it. Folders without a marker show as installed manually,
  one card per folder, with links to the web pages their `.toc` names
  (`X-Website`, `URL`, `X-Repository` and the like).
- **Addons changed by hand since**: each scan compares a marked folder's
  files with the marker's record, by length and time first and by hash
  only for those that differ there, so an addon the player edits or copies
  a build of over shows a Modified badge naming the files; Reinstall puts
  the installed version back. A marker from before files were recorded
  gets them at the next scan, from the folder as it is.
- **Addons installed before the launcher**: after each scan, unmarked folders
  that exactly match a catalog entry (every folder it installs is present)
  get that entry's marker. Bundles are matched before entries shipping one of
  their folders alone. The marker names the download whose recorded `.toc`
  versions best match the installed ones, or the preferred download when
  none does.
- **Addon data**: `WTF/Account/<account>/SavedVariables/<Addon>.lua` and the
  per-character `…/<realm>/<character>/SavedVariables/<Addon>.lua`, plus
  their `.bak` copies.

Archives are extracted to a hidden staging folder inside `Interface/AddOns`.
The walk goes breadth-first until it finds a folder holding a `.toc`. That
folder moves into place under the name its `.toc` declares, and the walk does
not descend into it, since deeper `.toc` files belong to embedded libraries.
So only `Name/Name.toc` layouts ever reach `Interface/AddOns`, whatever the
archive looks like. What an install replaces moves into another staging
folder, deleted once the new folders are in, so an install cut short (the
launcher killed) never leaves a folder half deleted. Staging folders an
install cut short leaves behind, here and beside `Wow.exe` for mods, are
deleted the next time the client is read, once untouched for an hour.

An update is offered when the catalog's `.toc` version of an installed
folder is newer than the one on disk, or differs from it without comparing.
Versions compare only when they have the same shape (`r736` and `r720`,
`1.2.3` and `1.3`, `1.19.5 (r240)` and `1.19.5 (r238)`); `r736` and `1.2`
do not. An installed version newer than the catalog's is said to be, and
offered a reinstall only.

The catalog's version of an entry is that of its first download, the newest
as the indexer orders them, unless the user picked a source on the card.
The pick is saved in the settings file (`sources`, by the entry's key: its
folders, lowercase, sorted and joined by `/`) and applied to every catalog
loaded: that source's download is the one installed and what updates are
measured against. Installing never falls back to another source, picked or
not: what the card says is what gets installed, and a failed download is
reported in the banner with the source named.

**Downloads from GitHub** sign in when they can, since GitHub limits
anonymous downloads, raw files included, with limits it doesn't publish.
The launcher stores no token. It takes `GH_TOKEN`, or else `GITHUB_TOKEN`,
from its environment, as the GitHub CLI does; or else, when the settings'
checkbox is ticked (`github_cli` in the settings file), it runs
`gh auth token` in the background, at start and whenever the settings open.
The token stays in memory. reqwest drops `Authorization` whenever a redirect
changes host, and every GitHub download redirects, so signed-in downloads
follow redirects themselves (`github::Signed::get`). They send the token to
github.com, api.github.com, codeload.github.com and
raw.githubusercontent.com only, never to signed release links or other
hosts. When GitHub answers 429, or 403 with no requests left, the banner
says GitHub is limiting downloads, and how to sign in when they weren't.
Downloads from GitLab stay anonymous: it allows anyone, signed in or not,
five repository archives a minute, so a token would change nothing. When
gitlab.com answers 429, the banner says to try again in a minute.

**The language** a client plays in is the one `WTF/Config.wtf` sets
(`SET locale`) when the client has a `Data/<locale>` folder for it, or else
the first such folder; its `realmlist.wtf` is the one that counts. With
several, the clients dialog switches it by rewriting that one line (the
rest of the file stays byte for byte, and the file is made if missing).

**Memory**: the game is a 32-bit program, given 2 GB of memory unless
`Wow.exe`'s headers carry the Large Address Aware flag, which gets it 4 GB
on 64-bit Windows and under Wine; HD textures and long view distances need
them. The clients dialog shows the flag as `Wow.exe` has it, and its box
sets or clears it: that one bit of the headers' characteristics, written
beside the file and renamed over, not while the game runs.

**While a client's game runs**, the launcher leaves alone what the game
writes back: `WTF/Config.wtf` when it quits, and the SavedVariables of
every addon it loaded when it logs out. So the language can't be switched,
saved settings can't be cleaned (on a card or as leftover data), an
uninstall keeps them, and an export that holds some can't be imported.
Installs, updates and repairs go ahead: the game never writes
`Interface/AddOns`.

**Play** starts `Wow.exe` from the client folder on Windows. Elsewhere it
runs the client's command with `sh`, the way Steam runs launch options: the
environment variables are set and exported first, and `%command%` becomes
the quoted path to `Wow.exe`. When there is no command, it is
`umu-run %command%` where `umu-run` is on the `PATH` (looked for once a
run), Proton through umu-launcher, or else `wine %command%`, and under
`gamemoderun` where GameMode's wrapper is on the `PATH` too
(`launch::Defaults`). `WINEPREFIX` is set first to the client's `.prefix`
folder beside `Wow.exe`, so each client has a prefix of its own that goes
with it, and a `WINEPREFIX` among the client's variables, set after it,
wins. Empty, the clients dialog's fields show what is used instead, and
under the environment variables a list says what the launcher adds, whole:
the prefix, and the mods' `WINEDLLOVERRIDES` (below).
`~` and `$HOME` expand as in a terminal. A command must have `%command%`,
since mods' setups run through it too: one without it (handing the game
to Lutris or Steam, say) is refused, as the clients dialog says under it.

**Mods** (`core/src/mods.rs`, `src/clients/mods.rs`) are looked for, like
the addons, whenever the client is read (opened, refreshed, or after
something was installed), as the list of mods describes them. A mod is
there when its marker is (recording the release installed, under `mods`
in the client folder's notes, below; the `.old_launcher-<id>.toml` of
earlier builds moves in there when read), or when one of its releases'
files is there with that release's contents, or several of them whatever
their contents: a lone `version.dll` of other contents is another mod's,
and a log it left behind is nothing. The player's files don't count:
uninstalling keeps them. What is there is checked at once: against the
release its marker names, or, without a marker, against every release,
the one whose files are all there as released being recorded in the
marker. Files that match none are a copy installed by hand, the player's:
the section says so, with the version its files say (`version_in`, or
else the `ProductVersion` of their version resource), offers the newest
release in its place, and the game starts with whichever of its DLLs are
there loaded. Nothing is said of a mod as released. Otherwise the launcher
needs to repair it before starting the game, which waits for it (Play is
disabled), and a banner above the addons says so: files missing or
changed, its setup not run to the end or what it creates missing,
`Config.wtf` set otherwise than it needs, or a release no longer listed:
Repair installs that release again, or the newest. Play waits too until
the client's mods were looked at, which happens once at a time per client
(asked again meanwhile, the look is repeated after it), and not while a
mod is being installed or removed there, which looks once done.

The marker records whether the setup ran to the end, since a setup cut
short can leave what it writes half written. A release recognized counts
as set up when what its setup writes is there.

Installing downloads the release, signed in when it is on GitHub, checks
every file against the list before anything changes, removes what was
there of the mod but the player's files, puts the files in place, records
the release, sets what `Config.wtf` needs, then runs the setup through the
client's command, the way the game starts (what it says goes to the
launcher's log), and records in the marker that it ran to the end. It is
the same runner, with the same environment variables (`WINEPREFIX`
among them), or none: a command that can't run another program fails the
setup rather than fall back to plain `wine`, which would update the prefix
to its own Wine. A `gamemoderun` the command starts with is left out,
though: GameMode is for the game, and a setup run under it lost its
output to the launcher. Off
Windows, Wine loads its own copy of DLLs such as
`version.dll` unless told otherwise, so the game starts with `name=n,b` in
`WINEDLLOVERRIDES` for each DLL the mods there put beside `Wow.exe`, while
they are as released (`launch::command`): set before the client's own
environment variables each time, as `WINEPREFIX` is, so a
`WINEDLLOVERRIDES` of theirs replaces it, and never saved in them. A mod's
setup runs without it. The clients dialog's Mods section says the same, and installs,
updates and uninstalls; uninstalling asks first, and deletes the player's
files only when ticked. Checking aside, none of it runs while the game
does.

Two mods conflict when they may put something at the same path, ignoring
case as Windows and Wine do (`mods::conflicts`, from the list alone: any
release's files, the player's, and what they and their setups write). A mod
can't be installed beside one there it conflicts with: the section says so
instead of offering it. Nor can it go where a file of something else is
(`mods::foreign`): one at a path of the release, not the player's, whose
contents match none of its releases, as another mod installed by hand
leaves. The section names the file, and installing refuses too. A mod
already there takes the files of its own release for its own, broken: a
repair puts them right.

**Clients from a torrent** (`core/src/torrent.rs`, `src/torrent.rs`,
`src/download.rs`): the add-client form takes a magnet link, the address
of a `.torrent` file or the file, and a folder to download into. The
engine is librqbit, started the first time a magnet link or a download
needs it, with a DHT it doesn't save. It listens for peers on a port the
system picks, which it asks the router to forward (UPnP), as games do, so
other players take pieces from it while it downloads. Its SHA-1 comes
from RustCrypto through `librqbit-sha1-wrapper/`, patched in over its
OpenSSL and ring options, so no C crypto library gets built.

Downloads go into a staging folder, `.download`, in the folder their
files go in, never among the client's files: librqbit writes the
pieces it downloads whole, over every file they share, and makes every
file of the torrent it doesn't find. librqbit writes each piece to disk
as it comes, and the download needs room on that disk alone (the player
may pick another disk because the others are full). Once a download is
complete, its files move into place, renamed within the disk (copied
beside their place then renamed over it, should the staging folder be on
another). `Wow.exe` keeps the Large Address Aware flag the folder's had.
The staging folder then goes.

A new client's torrent must hold a `Wow.exe` beside a `Data` folder, and
its files go into a folder named after the torrent, which must be missing,
empty, or hold only a download of it cut short. `Wow.exe` downloads alone
first, and its version is read; the rest once the player says so (turning
it down deletes the staging folder, and the folder made for it if that
leaves it empty). From then on, a copy of its `.torrent` is kept by info hash in
the data directory (`~/.local/share/old_launcher/torrents`,
`%APPDATA%\old_launcher\torrents`), and the settings file lists the
download (`downloads`: name, info hash, what the player gave, a file as its
magnet link since files go, and where its files go). A download cut short
resumes from a banner, librqbit checking what the staging folder has
first, or is discarded from it, staging folder and all. Once its files are
in place, the client is added, its torrent listed in `torrents` instead.
The download stops then: nothing more is shared.

Each client folder notes, in one `.old_launcher.toml` beside `Wow.exe`
(`core/src/notes.rs`), the torrent it comes from (`torrent`), the files
found as that torrent has them (`verified`), and its mods' markers
(`mods`). It is written beside and renamed over, one change at a time, and
deleted once there is nothing to note. A client forgotten and added back
gets its torrent back from there when the clients dialog reads the folder.

Checking for updates (clients dialog) fetches the torrent again from its
address or file (a magnet link's never changes), or else reads the copy
kept; with the copy gone, it asks the peers sharing it, by its magnet link,
or its info hash alone. A newer one replaces the copy kept, as long as it
holds the client in the same place. The folder is then compared with the
torrent piece by piece, only reading, leaving out the player's files
(`WTF`, `Interface/AddOns`, `Cache`, `Logs`, `Screenshots`, `Errors`, any
`realmlist.wtf`), the launcher's own `.old_launcher*` files beside
`Wow.exe` (a torrent made of a client folder carries them; they are never
taken from one either) and `Wow.exe`'s Large Address Aware flag. The files
whose every piece was read and matched are noted by length and
modification time, so the next check reads only the files changed since
(a piece shared with a file to download goes unread until it is, and so
do the files sharing it); a download notes those it wrote. A piece that differs and that several files share blames them all,
unless one of them differs anyway: downloading it writes the piece whole.

Any client can be given a torrent to update from (Set update source in the
clients dialog, or Change source), a magnet link, address or file as for a
new client. It must hold a client, in a folder named as the client's is
when it has it in one, since its files go where the torrent has them. It is
kept like a downloaded client's, and the client is checked against it.

Updating downloads the files that differ: copies of those there go into
the staging folder first, so only their pieces that differ download, then
only those files move into the client folder. The player's files are
never among them, so they stay as they are. A `Wow.exe` among them is
read in the staging folder first, and nothing goes in place unless it is
3.3.5a's: a torrent given may hold another game. An update stopped, failed
or cut short leaves the client's files as they were, and what it
downloaded in the client's `.download` stays for the next update to
resume from (librqbit checks what is there first); it goes once a check
finds the client current, or an update goes through. Quitting deletes what
a new client not yet said yes to downloaded. The files go in place once
the game is closed, and the game waits while they do. The dialog shows the
progress, the peers, the pieces, the speeds and the time left, and can be
hidden behind a banner.

**Quitting** (Ctrl+Q, or closing the window) asks first while something
it would cut short is under way: an addon being installed, uninstalled or
repaired, saved settings being deleted or imported, a mod being
installed, repaired or removed, or a client being downloaded or updated.
The dialog lists them.

**Showing the game on Discord**, when the settings say so (`discord` in the
settings file, off by default), runs the game's command as the child of the
launcher's own binary, started with `--discord` before the command
(`src/discord.rs`). That wrapper connects to the Discord desktop app's local
socket (a named pipe on Windows), sets the activity of the "Old Launcher"
Discord application, "Playing World of Warcraft 3.3.5a" with the time
played, and exits with the command's exit code when it exits, so the
launcher sees what it would without it. Discord clears the status when the
connection closes, so it goes with the game, whether the launcher is still
open or not. When Discord isn't running, the wrapper looks for it again
every 15 seconds. A wrapper that hands the game over and exits ends the
status with it. The application's ID is public and no secret is involved.

Outside the clients, besides the catalogs cached and the copies of the
clients' torrents, the only file lists the client folders, how each one
starts, the torrents they downloaded from, the sources picked per addon and
whether to use the GitHub CLI's login and to show the game on Discord:
`~/.config/old_launcher/config.toml` (`%APPDATA%\old_launcher\config.toml`
on Windows), or `$OLD_LAUNCHER_CONFIG` when set. If it can't be read, the
launcher does nothing else until you choose: it shows why, where the file
is, and which client folders overwriting it would forget, and offers to
edit it (then read it again), quit, or overwrite it with new settings.

## Layout

- `core/`: data and filesystem logic, no GUI and no network (TOC parsing,
  client detection, archive extraction, install/uninstall/repair/clean,
  the catalog schema, adoption, launch commands, the `library` the list
  is filtered from, the mods, and comparing a client with its torrent).
  Unit-tested against temporary directories.
- `indexer/`: the CLI that builds `index/wotlk.json` and `index/mods.json`
  from the upstream sources.
- `src/`: the [iced](https://github.com/iced-rs/iced) app. `lib.rs` is the
  shell, with one TEA cell per screen (`setup`, `clients`, `settings`,
  `download`, and `addons` with its cards and confirmation dialogs),
  `torrent.rs` wraps librqbit, `github.rs` signs downloads in to GitHub,
  and `discord.rs` shows the game on Discord. Screens are tested with
  `iced_test::simulator`, downloads between two librqbit sessions on
  localhost.
- `librqbit-sha1-wrapper/`: librqbit's hashes on RustCrypto (see above).
- `docs/plans/`: work planned but not started.

Nothing outside tests may panic on purpose: the workspace denies `unwrap`,
`expect`, `panic!`, `unreachable!`, `todo!` and `unimplemented!` through
clippy (tests are exempt, see `clippy.toml`). Whatever goes wrong while the
app runs ends up in the error banner at the top, which lists every problem
until dismissed.

## Tests

```sh
cargo clippy --workspace --all-targets   # also enforces the no-panic rule
cargo test --workspace
# Installs real catalog entries into a client, then uninstalls them
# (entries whose folders the client already has are skipped):
OLD_LAUNCHER_TEST_CLIENT="/path/to/World of Warcraft 3.3.5a" \
    cargo test --lib addons -- --ignored
# Downloads one file of each kind from GitHub, signed in with GH_TOKEN,
# GITHUB_TOKEN or the GitHub CLI's login:
cargo test --lib github -- --ignored
# Installs the newest Lumenveil index/mods.json lists into a temporary
# client:
cargo test --lib mods -- --ignored
# Joins the swarm of the torrent of a 3.3.5a client (a magnet link, or a
# .torrent's address or file), downloads its Wow.exe alone, reads its
# version, and turns the client down:
OLD_LAUNCHER_TEST_TORRENT='magnet:?xt=…' \
    cargo test --lib download::tests::a_real_torrent -- --ignored --nocapture
# Checks the folder that torrent downloaded into against it, twice, and
# says what an update would download. The check notes what it found in
# that folder: point it at a folder of links (cp -rs) to keep a client
# as it is.
OLD_LAUNCHER_TEST_TORRENT='magnet:?xt=…' OLD_LAUNCHER_TEST_TORRENT_CLIENT=/tmp/links \
    cargo test --release --lib download::tests::a_real_client_is_checked \
    -- --ignored --nocapture
# Updates a copy of that client, changed (a file removed, a byte changed:
# cp -a --reflink=auto makes one at no cost on btrfs and XFS), from the
# swarm, through a staging folder, then checks it again:
OLD_LAUNCHER_TEST_TORRENT='magnet:?xt=…' OLD_LAUNCHER_TEST_TORRENT_CLIENT=/tmp/copy \
    cargo test --release --lib download::tests::a_real_client_is_updated \
    -- --ignored --nocapture
# Moves a download's files from the temporary folder to a folder on
# another disk, which renaming can't do (a tmpfs /tmp and /home will do):
OLD_LAUNCHER_TEST_OTHER_DISK=~/somewhere \
    cargo test -p old_launcher_core torrent::tests::files_move_across_disks -- --ignored
# Makes a torrent of a client folder, only read, and checks a folder of
# links to it against it, twice:
OLD_LAUNCHER_TEST_CLIENT_FILES="/path/to/World of Warcraft 3.3.5a" \
    cargo test --release -p old_launcher_core torrent::tests::a_real_client \
    -- --ignored --nocapture
# Renders the README's screenshots from a demo client:
SCREENSHOT_CLIENT=/tmp/demo SCREENSHOT_OUT=/tmp/shots \
    cargo test --lib screenshots -- --ignored
```

The committed screenshots are rendered inside a container, so the demo
client sits at `/home/player/Games/World of Warcraft 3.3.5a` and the text
is drawn with iced's bundled font rather than the system's:

```sh
podman run --rm -v "$PWD:/src:ro" -v old_launcher-target:/target \
    -v ~/.cargo/registry:/usr/local/cargo/registry -v ~/.cargo/git:/usr/local/cargo/git \
    -v /tmp/shots:/out -w /src -e CARGO_TARGET_DIR=/target -e ICED_TEST_BACKEND=tiny-skia \
    -e "SCREENSHOT_CLIENT=/home/player/Games/World of Warcraft 3.3.5a" -e SCREENSHOT_OUT=/out \
    docker.io/library/rust:1.98.1 cargo test --locked --lib screenshots -- --ignored
```

The launcher says what it does on stderr; `RUST_LOG=old_launcher=debug` says more.

## The look

The launcher is drawn the way the game draws its login screens, as far
as their colors and shapes go (`src/style.rs`; the plan is
`docs/plans/wotlk-look.md`, with what was read off the game's textures
and `GlueXML`): white text on near-black, headings in gold capitals,
square frames edged in grey metal with a knob at each corner of a
dialog, blue glass buttons in a metal bevel (crimson for what deletes,
flat dark grey when they do nothing), grey-metal checkboxes ticked in
yellow, blue-black fields and tooltips, and the item-quality colors for
the badges (uncommon green, rare blue, legendary orange, poor grey).
Nothing is Blizzard's: the textures and fonts of the game are licensed,
so the knob and icons are the launcher's own SVGs in `assets/`, and
the headings are set in Cinzel, bundled under the SIL Open Font License
(`assets/fonts/`), the body in iced's own Fira Sans. The fonts are loaded
when the window starts and by the screenshots' simulator, so every system
draws the same thing. The SVGs' handles are made once (`style::Art`), so
the renderer finds each drawing in its cache without hashing the file
again each frame.

## Releasing

Pushes are only checked. A release is a push to `main` that changes the
version in `Cargo.toml` (render the screenshots again with it): its
pipeline builds the binaries and publishes them with the project page and
the `release.json` the launchers check for a newer version, all in one
Pages deployment that stays until the next release. If that pipeline
fails, push the fix and run a pipeline on `main` by hand (Build >
Pipelines > Run pipeline): a version not published yet is released then.
